# 威胁模型与安全设计（Threat Model）

> 本文档把「群点名应答制」「确认编号制」「忙碌让位」等协议条文重述为一套
> 显式的安全设计。**这些规则首先是防线，其次才是纪律。**
> 阅读顺序建议：先看「信任边界」，再看「威胁-防线矩阵」，最后看「残余风险」。

## 1. 资产与信任边界

```
┌─────────────────────────────────────────────────────────┐
│  IM 账户（最高信任根）                                    │
│  ├─ 指挥群（总线：所有跨机消息从这里过）                    │
│  ├─ Bot 应用（唯一发言人身份，代表所有 agent）              │
│  └─ 共享记忆表（结构化事实，跨机读写）                      │
└──────────────┬──────────────────────────────────────────┘
               │ ①轮询拉取（只读 API）
┌──────────────▼──────────────────────────────────────────┐
│  本地收件箱（半可信区：经点名/来源过滤后落盘的 JSONL）       │
└──────────────┬──────────────────────────────────────────┘
               │ ②会话开工时读取
┌──────────────▼──────────────────────────────────────────┐
│  Agent 会话（执行体：读收件箱 → 应答/执行 → 回群）          │
└──────────────┬──────────────────────────────────────────┘
               │ ③不可逆操作前
┌──────────────▼──────────────────────────────────────────┐
│  用户本人（唯一授权者：确认 #编号 才放行）                   │
└─────────────────────────────────────────────────────────┘
```

| 边界 | 信任级别 | 说明 |
|---|---|---|
| 用户本人 | 完全信任 | 唯一授权者，其消息即最高指令 |
| IM 账户 | 完全信任（但是单点） | 群、bot、记忆表都挂在它下面，见残余风险 R1 |
| 群消息通道 | **不可信输入面** | 任何进群者发出的消息都可能被 agent 读到——这是本模型最大的攻击面 |
| 本地收件箱 | 半可信 | 已经过点名/来源过滤，但内容本身仍可能含注入文本 |
| 轮询器 | 最小权限组件 | 只做「拉取 → 过滤 → 落盘」，设计上不具备回复与执行能力 |

**核心设计立场：群消息是外部输入，等同公网数据，永远不默认可信。**

## 2. 威胁-防线矩阵

### T1 群消息 prompt injection
**场景**：群里出现恶意内容（被拉进的旁观者、被入侵的其他成员、或 agent 之间的间接注入），
试图诱导某台机器的 agent 执行危险指令。

**防线**：
- **点名应答制**：agent 只处理形如 `→ @机器名-软件名` 的精确点名消息；未被点名的 agent
  不得应答、不得抢答、不得「顺手」执行。攻击面从「全体 agent」缩小到「被点名的那一个」。
- **来源过滤**：轮询器只把「点名本机的 bot 消息 + 用户本人消息」写入收件箱，其余直接丢弃，
  注入内容根本到不了会话。
- **纵深**：即便被点名，**不可逆操作（删除、外发、改配置等）仍必须走 T3 的确认流程**——
  点名只解决「谁响应」，不解决「能不能做」。

### T2 伪造点名
**场景**：消息正文里手工拼出 `→ @机器名` 字样，冒充路由指令。

**防线**：
- 轮询器同时校验 `sender_type`（bot/user）与消息前缀格式，system 消息与异常结构直接丢弃；
- 高危指令必经 `#编号` 人工确认（见 T3），伪造点名最多换来一条「待确认」摘要，无法直接落地；
- 建议部署方将群成员收敛为「1 个人 + 1 个 bot」（本协议的参考形态），从成员侧消灭伪造源。

### T3 agent 冒充授权
**场景**：某个 agent 在群里回复「确认 #1234」，试图让另一个 agent 误以为授权已下达。

**防线（授权唯一性三条件）**：
1. 只有 `sender_type == user` 且身份匹配授权者的回复才可能构成授权；
2. **任何 agent 消息一律不算确认依据**，无论内容多像用户的口吻；
3. 跨会话补认（离线期间错过的确认）必须同时满足：
   **编号可溯 + 命令与原始请求一致 + 确认时间在 24 小时内**，三者缺一即重新发起确认。

### T4 确认悬挂
**场景**：agent 发出「待确认 #1234」后用户一直不回，会话被无限阻塞。

**防线**：超时放弃——等待确认期间以固定间隔重读**本地收件箱文件**（本地 IO，零 API 零 token），
超过时限（参考值 10 分钟）主动放弃并回群说明。绝不无限等待。

### T5 确认重放
**场景**：agent 离线期间群里的旧确认，在新会话中被当成新授权执行。

**防线**：T3 的三条件中「24 小时内」与「命令一致」专杀重放：过期或对不上号的确认一律作废，
宁可重新打扰用户一次，不可错放一次。

### T6 重复执行
**场景**：同一条点名消息被处理两次（重复会话、重装、游标丢失）。

**防线**：双层去重——
- 轮询层：`seen` 游标记录已见 message_id，只 append 新消息；
- 应答层：值守维护 `processed_ids`，回群成功后才 `--mark-done`，未标记的候选每轮重新列出但由
  应答侧判断；游标与状态文件都只保留最近 500 条，防无限膨胀。

### T7 多源指令竞争
**场景**：定时值守 agent 与用户正在交互的会话同时操作同一台机器，互相踩踏。

**防线**：忙碌让位——值守启动时先检测「本机最近 N 分钟（默认 15）是否有会话回合落库」，
有则输出 `BUSY` 并整体静默。检测只读本地数据库/状态，窗口内值守对一切点名装死，
把机器让给用户面前的交互会话。

### T8 轮询器失控
**场景**：常驻轮询组件如果具备回复/执行能力，一个 bug 或注入就能让它自行行动。

**防线（纪律固化在代码里）**：轮询器**只写本地文件，绝不自动回复、绝不自动执行任何命令**
——这不是文档口号，是解析器的实现边界：它只调用「读 API + 写 JSONL」，没有发送与执行代码路径。
所有「行动」都由后续的 agent 会话在人的视野内完成。

### T9 确认消息泄密
**场景**：待确认消息里贴出 token、密钥、内网地址，群聊成为敏感信息外泄渠道。

**防线**：确认最小化——只发「编号 + 一句话摘要与影响」，敏感内容留在本机，群里只有脱敏摘要。

### T10 文件/媒体消息盲区
**场景**：指令或注入内容藏在 file/media 消息里，绕过文本收件箱的全部过滤。

**防线（当前为已知盲区，如实声明）**：轮询器只捕获文本消息，文件与媒体消息**不落收件箱**
（双向后果：既收不到正经文件，也不会未经处理地进入 agent 上下文）。缓解约定：
跨机传文件改走专用通道（网盘/存储桶），文件本体不进指挥群；需要交接时在群里发「文件已就绪 + 位置」的文本。

## 3. 残余风险（诚实清单）

| # | 风险 | 现状与缓解建议 |
|---|---|---|
| R1 | IM 账户即信任根：账户被盗 = 总线 + 记忆库同时失守 | 依赖平台侧账号安全（两步验证等）；bot 权限按最小化申请；**记忆表只存提炼后的事实，敏感片段只留本地** |
| R2 | 用户本人被社会工程：群里诱导用户说「确认」 | 技术无解，靠确认消息的「摘要+影响」格式帮用户看清后果；用户对编号存疑时应拒绝 |
| R3 | 本地收件箱/状态文件明文落盘 | 属于本机磁盘边界；建议收紧目录 ACL，敏感环境可加密 home 目录 |
| R4 | 轮询间隔带来的确认延迟窗口 | 等待期靠本地文件重读兜底；如需秒级确认，缩短轮询间隔或加 webhook 通道（平台能力允许时） |
| R5 | 单用户模型：多人协作场景未设计 | 协议明确面向「一人多机多 agent」；多人团队需先扩展授权者模型，本版本不承诺 |

## 4. 与推送式审批方案的安全权衡

托管平台（如带手机 Approve/Deny 推送的方案）把确认做在平台侧：到达快、体验好，
但要求自托管服务端或平台在线，且审批通道与总线合一。
本协议把确认做在**群聊文本协议层**：多一层「伪造文本」的攻击面（由 T2/T3 防线覆盖），
换来零常驻服务、离线可补读（三条件校验）、以及「确认记录天然是一份可审计的群聊日志」——
谁在何时批准了什么，群里翻记录即可回溯，不需要额外审计设施。

## 5. 部署方检查清单

- [ ] 群成员收敛为「1 人 + 1 bot」，不拉第三方
- [ ] bot 权限最小化（读群消息 + 发群消息 + 所需的表格权限，不申请多余 scope）
- [ ] 机器名与软件名使用**不含个人信息**的代称（不要用真名、硬件型号、邮箱前缀）
- [ ] 确认超时、忙碌窗口、24h 补认时限三项参数已按团队节奏调整
- [ ] 跨机文件传输已改专用通道，指挥群只走文本
- [ ] 记忆表只存提炼事实；密钥、token、客户数据一律只留本地
- [ ] 本地收件箱目录权限已收紧（仅本机用户可读）
